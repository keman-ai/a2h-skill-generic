# 📦 托管建档剧本（intake）

> 用户说想清东西、随口报了一件要卖的，或发来物品照片时读本剧本。
> 目标：把用户的动作压缩到**一句话（或拍照）+ 30 秒过目清单**，其余全部由你完成。

> **适用范围**：本文件 = 建档**公共工序库** + GOODS 卡（card-goods.md）的工序细节；
> 其他帖型的**要素**以各自 card-*.md 为准（判卡见 SKILL.md「先判卡」），
> **工序**（口述落位 / 确认门 / 敏感检查 / 追问上限 / 币种必问）全帖型通用。

## 流程总览

```
收话/收照片 → **逐张看图（§2.1）**
→ 【一张图里不止一件时】**拆件 + 确认门 1（§2.4.1 / §2.4.2）**——它整段插在这里，
  在**建档之前**：一坨照片得先知道是几件、哪块是哪件，才谈得上一件件抽字段
→ **敏感信息检查（§4，在传图之前）** → 抽字段建档
→ 按需追问（三态见 §2.3，上限见 §3）
→ 【多件时】**门 2 出封面（§2.4.3）** → **口述落位核对（§5.0）** → 输出托管清单
→ 用户确认 → 进入定价与授权
```

## 0. 一句话就能开工

"那个电饭煲九成新，30 出了"——这样一句话就足够开始建档：

- 把话里带的字段全部抽出来（品名 / 成色 / 价格 / 任何顺口说的信息），缺的按 §2 生成、按 §3 判断要不要补问；
- **没有照片不是障碍**：无图也能建档上架，清单和描述里标「暂无图」；
- 发布后**轻轻补一句**："补张图被联系的概率会高不少，随时发给我就行"——
  补图是可选的第二步，**绝不把拍照做成发布的前置条件**，也不要在确认前反复催图。

用户常常是先想起来说一句，照片还在手机里。以拍照为前置会挡掉这批人。

## 1. 收照片

照片有两个来源，处理完全相同：

- **会话里直接发**；
- **手机寄件通道**（`~/.a2hmarket/inbox`）：**会话开场巡查**发现新寄件 → 读对应目录的 message.txt 和照片，按附言意图走流程。

**入口引导（时机化推荐，不主动推销）**：
- 用户说"照片在手机上/手机拍的怎么给你"→ 已接通道：告知"手机上打开寄件页拍照寄我就行"；未接：推荐 phone-inbox（"功能上线通知群里有包，我帮你装好并把二维码发你"），装好后 `ln -s <工具目录>/inbox ~/.a2hmarket/inbox` 完成接入；
- 建档过程中用户提到"还有几件回头拍"→ 顺口提一句手机寄件，不展开；
- 每次成功收到寄件，回执一句"收到，手机拍完随时寄"——强化习惯。

- 用户可以一次发一件，也可以一次发一堆（批量是常态，鼓励"把要清的都拍来"）；
- 每件 1 张照片就能开工；建档后若照片不足以让买家判断成色，礼貌请用户补 1–2 张关键角度（正面 + 瑕疵处）；
- 用户顺口说的信息（"这个买了三年了"）全部记入建档，不要让用户重复。

**📎 上架要用的是本地文件路径**（照片现在能直传集市了，见 marketplace.md §A）：
- **手机寄件通道**的图本来就在磁盘上（寄件目录里），直接拿那个路径传；
- **会话里直接发的图**：你能看见它、但不一定拿得到本地文件路径。**先试宿主取图法**
  （下条），取不到再请主人把图存到电脑上告诉你路径（一句"存桌面就行，告诉我文件名"即可）。
  **别为这个卡住建档**——建档、定价、写描述都不依赖上传，图可以最后再补。
  - **Claude Code 宿主取图法**（0805 实测可行）：会话 transcript 落在
    `~/.claude/projects/<项目目录名>/<会话id>.jsonl`，主人粘贴的图以 base64 存在
    `message.content[].type=="image"` 块里。逐行扫 jsonl、解码 `source.data` 写到
    `/tmp/chat-image-N.jpg`，**用 Read 工具肉眼核对是哪张**（按时间戳对应粘贴顺序），
    再走 `photo upload`。注意：transcript 可能有多张图，**核对后再传，别按序号赌**；
    其他宿主没有这个通道，老实请主人给路径。
  - 🔴 **照片状态的用词必须如实**（真机踩过）：拿不到文件时，托管清单和上架报告里
    写「**暂无图**（你发的图我看得见但取不到文件，存本地告诉我文件名就能挂上）」——
    **绝不写"暂用这张 / 图已挂上"**这类会让主人以为照片已附上的话术。
    主人是看了清单确认才上架的，清单上的每个字都是承诺；
  - 上架完成的报告里**再提一次**图的真实状态（有图几张 / 无图 + 怎么补），
    不要让主人事后自己发现帖子是光板的。

## 2. 建档（识图 / 听话）

> 开工前扫一眼**偏好档**（[preferences.md](preferences.md)）：主人的交付习惯、赠送倾向、
> 好归宿观都影响建档与追问的默认值；建档过程中主人顺口说的稳定偏好也随手记回偏好档。

### 2.0 🔴 四问：每条帖子必须答全（单品、合集一视同仁）

不管一张图里是一件东西还是十件，**成品描述必须让买家读完就知道这四件事**：

| # | 问题 | 落在哪 |
|---|---|---|
| ① | **是什么** | 品名 + 品牌/型号 + 关键规格（"Loveramics 黄色咖啡杯碟套装"，不是"杯子"） |
| ② | **什么状况** | 成色、瑕疵、配件齐不齐、用了多久 |
| ③ | **多少钱** | 单品填 `--price`；**合集逐项列价**，有打包价就写明 |
| ④ | **怎么交易** | 自提/邮寄、地点、可交易到哪天、以及卖家提的条件 |

**答不全就别急着上架**——缺 ① 的帖子搜不到、缺 ③ 的帖子买家不会点进来。
真的问不出来（主人也不知道）就在描述里如实写"未知"，不要编。

#### ④「怎么交易」的信息往哪放：**按能不能筛分流**

交易信息形态很杂——自提/邮寄、邮编、地铁站、"可留至 8.7"、"多买多送"、"可小刀"。
**别想把它们都塞进枚举**（枚举装不下，也永远列不完），按这张表分流：

| 信息 | 去处 | 为什么是它 |
|---|---|---|
| 自提 / 邮寄 / 同城送 | `--delivery`（枚举） | 买家要筛「可邮寄的」 |
| 面交地点、邮编、地铁站 | `--meetup`（多值文本） | R17 按面交范围过滤要用 |
| 可交易到哪天 | `--available-until` | R11 到期自动下架要用；**原帖写了具体日期就填它**，别用默认 +14 天 |
| 时段 / 条件 / 要求 / 议价空间 | **描述里的【交易】行** | 无法穷举，只需人读，不参与任何筛选 |

判据就一句话：**这条信息将来会被拿来筛选或排序吗？** 会 → 结构化字段；不会 → 描述。
所以「可小刀」「多买多送」「只收现金」「晚上 6 点后」一律写进描述，不要为它们发明新字段。

**【交易】行高频信息清单**（0811 从 1143 条真实帖挖出——用户常写、此前无引导，
AI 代写的帖子不该比用户手写的信息更穷）：

| 信息 | 处理 |
|---|---|
| **可预留至 X**（"9 月来的新生可以留给你"） | 提了必写——毕业潮与新生潮错峰一个月，这句是跨档期成交的钥匙 |
| **多段交接窗口**（"8.8-8.10 或 8.24-8.26 有空"） | 有几段写几段、**原样写清**；`--available-until` 仍填最早截止，多窗口进描述 |
| **定金/预留规则**（"非当天取需定金留物，跑单不退"） | 提了必写。🔴 纪律：如实转述主人的规则，**不代收、不背书、不替双方设计定金方案** |
| **结算方式/可收币种**（"可 rmb 付"） | 提了必写；标价币种 ≠ 可收币种，别混为一谈 |
| **邮费谁出 + 付款顺序** | 勾了邮寄就在托管清单上**强烈建议补充**（标注"写清省掉九成邮寄扯皮"，不追问）——邮寄纠纷第一来源 |
| **送货/帮搬条件**（"超 £4 送到地铁站""家具自行搬运"） | 提了必写，条件（门槛/范围/顺路）原样带上 |
| **先到先得/优先规则**（"直取优先""打包优先"） | 提了必写；后续议价时这是排序规则，接待买家要转述 |
| 交付前清洁承诺（"出前会消毒"）、代卖声明（"帮朋友出"） | 提了才写/读到必落——一句话的信任加分项 |

抽取时的坑（都是实测踩的）：

- **英国邮编要按邮区前缀白名单认**（E/EC/N/NW/SE/SW/W/WC/BR/CR/…）。只按形状匹配会把
  图片编号 `P1`、纸张尺寸 `A4`、显示器型号 `27G2U` 当成邮编；
- **`pt` = Parcelforce**（留学生圈简写「可走 pt」＝可邮寄），别漏；
- **地点去重要留短的**：「伦敦waterloo附近」和「Waterloo」是同一个地方；
- **正文没写取货方式就留空**，不要替卖家默认成自提——猜错会让买家白跑一趟。

⚠️ **帖子级字段装不下逐项差异**：实测有帖子写「咖啡机和锅可留至 8.17，其余 8.7」，
帖子只有一个 `availableUntil`，只能取较早的那个。这类逐项差异（逐项价格、逐项时限、
逐项售出）要等「帖内子项」能力，现阶段在描述里如实写清楚。

### 2.1 🔴 看图是**必做动作**，不是可选项

**有图就必须逐张看过再建档**——不是"有空看一眼"，是和写标题、定价同级的必经步骤。

> 🔴 **看图是工序，不是内容**。看图的产出是**商品事实**（型号、瑕疵位置和程度、
> 配件齐不齐、图上的标价——标价的处理见 §2.1.2），把它们**融进描述正文**——
> **不要在描述里写"看图说明"这一段，也不要写过程**。
>
> ❌ 反例（真实踩过）：描述里写「6 张全看：①白底网页+手指指向瑕疵处；②③同一张
> 重复上传；④⑤可见一道很淡的细线…」——「看了几张」「哪张重复」是**我们的审计信息**，
> 买家和买家 agent 一个字都不需要，还把真正有用的「屏幕有道淡线、白底可见、
> 游戏中基本不可见」埋在了中间。
>
> ✅ 正解：「屏幕有一道很淡的细线，白色背景下才看得出，游戏画面中基本不可见；
> 已实测 240Hz / FPS2 游戏模式正常。无原包装盒。」

没看图就建出来的档，典型症状是描述只会复述主人那句话、买家最关心的成色和瑕疵一个字没有——
而**这些信息只存在于图里**（"有瑕 在后面两张实况里"这种正文，不看图等于没写）。

> 无图的帖子照常建档（标「暂无图」），这条只约束**有图**的情况。

**看图得出的关键判断（价格、品名、成色）要连依据一起写，不能只给结论。**
一句"红字是件号"和"红字是件号——因为同一个数字在 4 件不同衣服上重复出现，
而件号不会重复"，可信度完全不同：前者无法被质疑也无法被推翻，后者能被检验。

> 实测（同一批图两次判断得出相反结论）：先判"图上红色数字是件号"，复核时发现
> **同一个「2」出现在 4 件不同衣服上**（件号不会重复）、有一张带手写 £ 符号、
> 还有一张写的是汉字「送」而非数字，且 2×4=8 与正文「打包 8p」吻合——
> 结论反转为**单价**。有依据的那次赢了，靠的不是更用力地看，是把依据摆出来。

**判断不了就说判断不了**：「品牌字拍糊，认不出」「没拍吊牌，全新无法核实」
都是合格的输出。编一个像模像样的品牌型号，比留空糟得多。

### 2.1.1 信息来源：**图优先**，不是文字优先

二手帖的形态是**图为主、正文为辅**：品名、价格、成色常常只画在图上（拼图标价、
手写标签），正文只写地址和时限。所以**必须真的看图**，把图当成第一信息源。

**别用 OCR 代替看图**——OCR 只抠"已经是文字的像素"，答不了「这是什么东西」，
还会把网页页脚、包装印刷、店铺水印当成商品信息。实测踩过的坑：

| 图长什么样 | 怎么读 |
|---|---|
| **拼图标价表**（九宫格，每格一件 + 价签） | 逐格抽「品名 + 价格」，这是合集帖信息量最大的一张 |
| **单件实拍** | 判品名、成色、瑕疵、配件是否齐全 |
| 图上有**手写数字** | 可能是**件号**不是价格——与正文交叉验证再定（"打包 8p" + 图上写 1/2/3 = 9 件共 £8） |
| 图上有**店铺水印 / 模特街拍** | 多半是**商家营销帖不是个人闲置**，按 §4 剔除 |
| 图是**网页截图** | 只取商品本身信息，导航栏/页脚/客服条款一律不进描述 |
| 价格被**马赛克遮住** | 如实写"价格图中被遮"，不要猜 |

### 2.1.2 🔴 图上有标价 = 用户已经定过价，不要再"建议"

图上读出标价（价签、拼图标价表、手写 £/¥ 数字）时，**那就是挂价**，不是"参考信息"：

- **直接按图价建档**：托管清单的挂价列写图价，并注明「（图上标价）」；
- **不给定价建议**——不做行情分析、不评价高低、不说"建议挂 £xx"。
  [pricing.md](pricing.md) 的建议价流程只服务**没有价**的物品；
  用户主动问（"这个价合理吗""多少钱合适"）才启动它；
- **币种按图上符号/文字直采**（£、$、¥、"磅/镑"、"元/块"）：图上是 ¥ 价就挂 `CNY`，
  **不要因为站点默认 GBP 就改标或换算**——错标币种的帖子，买家看到的是离谱价
  （种子数据里英镑/人民币混标就是这么来的）；
- **只有数字、认不出币种**（如手写"15"）→ 必须问一句「图上的 15 是英镑还是人民币？」，
  **不许默认猜**。这一问不占 §3 的两问额度——价格错标比多问一句伤得多；
- 图价和用户嘴上说的价**冲突** → 以用户的话为准，清单备注里写明
  「图上标 £20，按你说的 £15 挂」——让用户有机会纠正是哪边错了；
- 价格被遮/拍糊 → 如实标"价格图中不清"，按无价物品走 pricing.md。

### 2.2 字段

对每件物品，从照片和用户的话推断并生成（无图时全凭描述，能生成多少是多少，缺的留空）：

| 字段 | 生成要求 |
|------|---------|
| 标题 | 品名 + 型号/规格 + 关键卖点，≤20 字。能从照片认出品牌型号就写全（"Kindle Paperwhite 4 8G"），认不出就写清品类特征 |
| 描述 | 2–4 句，口吻真诚不像广告：什么东西、为什么出、适合谁。**"适合谁"必写**——这是好主人匹配的种子。**末尾自然带 2–4 个 `#标签`**（小红书笔记式：品类、场景、课程代码都行，如 `#厨房 #小家电`）——标签只写在正文里，服务端会解析成检索索引<br>🔴 **描述 = 商品信息本身**：读它的主要是买家的 agent，它要一次读懂「是什么·什么状况·多少钱·怎么交易」。所以**不要重复结构化字段已有的东西**（成色、价格、成交方式各自有字段，别再写一遍「【成色】轻微使用痕迹」），**也不要写我们的加工过程**（看了几张图、哪张重复、OCR 抠到什么）。只写**关于这件东西本身的事实** |
| 主分类 | 自由文本，从标签里挑最主要的一个（如「厨房」）填 `--category`；不再是固定枚举 |
| 属性 | 抽到什么存什么的开放键值（品牌/容量/尺寸/入手渠道…），`--attr 键=值`；没有就不填 |
| 成色 | 全新/几乎全新/轻微使用痕迹/明显使用痕迹/能用有瑕疵——从照片/描述保守判断，宁可低估不高估 |
| 瑕疵说明 | 照片里看得到的瑕疵**必须**如实写；这是熟人半熟人交易不伤感情的底线 |
| 规格参数 | 认出品牌型号后**检索官方/电商资料**（宿主可联网时），提炼买家最关心的客观信息（关键参数、功能依赖如"需 App/订阅/联网"、包装清单），末行注来源和日期；检索不到或宿主无网 → 用模型知识填并注明"凭模型知识，未核实"。**这一步做足，买家 agent 就不用来问功能问题** |
| 新品参考价 | 检索同款新品当前价写入（同时是 pricing.md 定价的锚）；停产/查不到 → 填同类替代品新品价并在规格参数注明口径 |

**一帖多物（合集）时额外做三件事**——集市检索只认文字、照片不参与检索，
所以图里有什么必须变成文字，否则买家搜「微波炉」永远搜不到那条清仓帖：

1. 🔴 **描述开头写分件清单——一件一行、行首编号**。这不只是排版，是**双方 agent
   共守的读写约定**：买家的 agent 也按这个格式解析合集帖（marketplace.md §B），
   写歪了对面就读不出来。格式：

   ```
   本帖包含 4 件（可指编号问）：
   1. 微波炉（Panasonic 800W 微波炉）——£10 · 九成新
   2. 电视（LG 43寸 电视机）——£40 · 屏幕左下有小划痕 · 仅自提
   3. 山地自行车（单车）——£60 · ❌已出
   4. 台灯——送，随任一件附赠
   整套打包 £85，一次拿走优先
   ```

   每行固定顺序 **品名（叫法变体）——价格 · 成色/瑕疵 · 逐件例外 · 状态**，每个讲究都有用途：
   - **行首编号是锚点**：买家串里问"2 号还能便宜吗"、回归简报对账"3 号出了吗"都指得准，
     两台同款也不歧义。编号与 §5 托管清单对应件一致——主人、买家、两边 agent 说同一套号。
     **编号一经发布不重排**：卖掉的行保留原号标 ❌，后补的件续号，锚点才稳；
   - **品名带叫法变体**（括号里）：集市检索按字模糊匹配+相关性排序（0811 实测），
     变体写得越全，**相关性排序越靠前、英文词才搜得到**。
     写成「陶瓷平底锅（陶瓷锅）」「戴森 Dyson 吸尘器」，中英文、长短叫法各写一次，
     几乎零成本；买家最可能打的**短词**再放进 `#标签`（精确匹配通道）；
   - **抽不出价的行只列品名**，白送的写「送」；**打包价固定放清单末行**——
     想一锅端的买家和 agent 都在固定位置找到它；
2. **标题补主品类词**：`伦敦出二手` → `伦敦出二手：微波炉/电视/自行车`。
   卡片上买家只看得到标题、价格、成色徽章、地点、封面图——**描述有封面图时不渲染**，
   标题是唯一能透出"里面有什么"的位置。标题已经点明品类的（"画材&水彩纸"）就别再堆；
3. 🔴 **逐件不同的信息写在各自行里，不糊成一团**：成色、瑕疵、「仅自提」「可留至 8.17」
   这类逐件例外全落行内。「整体八成新」这种把十件东西的成色捏成一句的描述**不合格**：
   买家关心的是他要的那一件，捏在一起等于每件都没说。真正全体共用的（同一取货地点、
   统一时限）才写在清单外的正文里。单件卖掉时只改那一行标 `❌已出`
   （操作见 marketplace.md §A「合集帖里卖掉一件」），全部出完才整帖 SOLD。
   清单超过 ~8 行、或逐件信息多到行内塞不下，正是下面「超 ~10 件拆帖」该触发的信号——
   硬要合一帖就以「等 N 件」收尾，但记住：**没写进清单的件搜不到，等于没挂**。

合集的 `--price` 留空（面议）或填**打包价**；单件价格写进清单行。
帖级 `--condition` **按最保守（成色最差）的那件填，或留空**——逐件成色已在
清单行里，帖级字段别拿最好的那件撑门面（成色徽章是买家第一眼看到的）。

**毕业清屋（整批打包卖）再加三条**：

- **目录留白与上门自选是合法形态**（0811 实测 7–10% 清仓帖在写）：主人说
  "还有没拍的，谁要什么来问"或"欢迎来家自选"时，描述末尾固定加一行
  「清单外仍有杂物可询 / 可上门自选」——这不是清单没写全，是**有意留白**，
  如实保留，不要为了"清单完整"逼主人把家底拍全；

- **打包价主动问一句**："整套一起拿走算多少？"——毕业卖家的真实心态是**最好一锅端**，
  打包是主路、拆卖是兜底。打包价按单件合计的 7–8 折给建议（用户已报打包价的照旧
  不建议，见 §2.1.2 口径）；描述里打包价写在清单行之后（"整套打包 £60，一次拿走优先"），
  让"想全要的买家"第一眼看到；
- **超过 ~10 件建议按房间/品类拆帖**（厨房一帖、卧室一帖、电器一帖）：几十件塞一帖，
  标题装不下、买家搜到也翻不动。拆帖对卖家零成本（照片本来就是分房间拍的），
  对检索是量级提升。用户不想拆就不拆，一帖也能发（清单行照写）。

### 2.3 🔴 要素三态表：每个要素缺了怎么办

§2.0 管"描述读起来全不全"，这张表管**每个要素该问到没问到、缺了怎么处理**。
总原则不变：**任何要素都不拦发布**——问过没答的标「未知」照发，
托管清单会让用户自己看见缺口（§5）。

| 档 | 要素 | 落点 | 缺了怎么办 |
|---|---|---|---|
| **A 必须成立**（认不出就问，**不占 §3 追问额度**） | 品名 | `--title` + 描述 | 图和话都认不出是什么 → 必须问一句。没有品名根本无从建档，这是唯一的例外 |
| | 币种 | `--currency` | 只有数字认不出币种 → 必问不默认（§2.1.2 原规则）。错币种比缺价格伤得多 |
| **B 优先消费追问额度**（§3 的两问额度优先花在这里） | 面交地点到楼 | `--meetup` / `--location` | 只到城市 → 追问到公寓/宿舍楼/地铁站。"我拿不拿得到"靠它回答 |
| | 能否正常用（数码家电） | 描述 | 图判断不了 → 问。买家最关心、图上最看不出的一项 |
| **C 尽量抽取，缺了标未知照发，不为它问** | 价格 | `--price` | 图价/口述价按 §2.1.2；都没有 → pricing.md 建议价或留空面议 |
| | 成色 | `--condition` | 从图保守判断；判不了标未知 |
| | 瑕疵 | `--flaw-note` + 描述 | 图上看得见的**必须写**（这条是硬的）；无图如实写"未验" |
| | 交易方式 | `--delivery` | 没说就留空，**不默认自提**（§2.0 原规则） |
| | 可交易时限 | `--available-until` | 原话/原帖有日期填它，没有默认 +14 天 |
| | 打包价（合集） | 描述清单行 | 主动问一句"整套算多少"（§2.2 毕业清屋规则），不答就只列单价 |
| **D 禁问**（用户提了才记，一律不问） | 购买年份、原价、离境日、配件齐不齐、尺寸重量、包装还在不在 | `--attr` / 描述 | 提了就记进落点，没提**当它不存在**。这条清单直接护着"愿不愿意发" |

**合集帖里 A 档按件生效**：每一件的品名都必须成立（清单行里"等 N 件"收尾的除外）——
搜不到品名的那件等于没挂。B/C 档在合集里逐件过一遍，但追问仍合并问（§3），不逐件轰炸。

**类目要素补充**（0811 从真实帖挖出的品类硬信息——按品类触发，不进上表通用档）：

| 品类 | 要素 | 处理 |
|---|---|---|
| 服饰 | 尺码 + 卖家上身参考（"163cm 偏瘦供参考"） | **提了必写**（身材信息绝不主动问）——真实服饰帖的标配，买家判断合身的主依据 |
| 小家电/数码 | 插头制式（英标/中标/带转换头） | **尽量抽取**——图上认得出就写；留学生场景买错制式 = 不能用 |
| 高价数码（手机/平板/电脑） | 解绑承诺（iCloud/账号已抹除）、可验证渠道（可当面验机/可走平台验证） | **强烈建议补充**——托管清单上标注"写一句成交更快"，不追问 |
| 家具大件 | 谁搬（自行搬运 / 可帮搬及条件） | 尽量抽取 |

### 2.4 🔴 一图多物：拆件 → 确认门 → 出图

> **什么时候走这一节**：主人发来的**一张照片里不止一件东西**（"拍了一堆你看看"是常态）。
> 这不是一个要启动的模式，没有"开始拆件"这种命令——看图发现不止一件就顺着往下走。
> 一件一张的照片不走这节。

主人把要清的东西往桌上一摊拍一张，今天他答不了的问题只有一个：
**"我这张随手拍的照片，到底能不能就这么发出去？"** §2.2 的分件清单已经能把每件**说**清楚，
这一节负责把每件**指**清楚：一张能一眼对上的确认图、每帖各自的封面。

三个名词，全篇只用这三个：

| 名词 | 是什么 |
|---|---|
| **框** | 你**看图**得出的一件物品的大致矩形 `(x0,y0,x1,y1)`，刻意宽松，容忍不精确 |
| **物项表** | 当轮的一张表 `[{序号, 名称, 框, 颜色, 归哪条帖}]`。🔴 **不落盘**，它**长成** §5 的托管清单，不是第二张表 |
| **加工脚本** | `scripts/annotate.py`——只读原图、把框画成图，出参是临时目录里的图片路径 |

🔴 **序号的唯一真相源是帖子描述里的分件清单**（§2.2 的行首编号），不是物项表：

- 物项表当轮就没（框数据不落盘），换个会话重新看图必然重排；分件清单写在服务端的
  description 里，长期活着，而且买家的 agent 也按它解析（marketplace.md §B）；
- ⇒ **发布前序号随便重排，发布那一刻固化**。此后卖掉的行保留原号标 `❌已出`、
  后补的件续号（marketplace.md §A），出图侧同守：已出的件**原位打叉、号照旧**；
- ⇒ 🔴 **重出任何带号的图之前，先把帖子描述读回来**（`a2hmarket.py listing mine` 或
  `a2hmarket.py market show <id>`），把描述存成一个文件，用 `--numbering listing
  --listing-description-file <文件>` 出图。**读不回来就不出图**，跟主人如实说一句
  "清单读不回来，我没法保证图上的号和帖子里的号是同一套，先把帖子取到手"——
  不许退而求其次按当轮识别的号画：图上 3 号 = 清单 4 号是**静默**错位，
  没有任何地方会报错，而买家是点着号来问的。脚本会拒绝，别绕过它；
- ⇒ **拆帖之后没有帖内编号**（一帖一件、描述里没有清单）。当轮说"3 号"只在当轮有效，
  这一条要如实告诉主人："拆成 N 帖之后各是各的帖了，回头你说『那个相机』比说『3 号』准"。
  **不为拆帖发明一套跨帖/跨会话的编号**；
- ⇒ 序号**不进文件名、不进图片元数据、不进 `--attr`**——那等于在集市上立第二份编号真相源。

#### 2.4.1 拆件：报框 → 物项表 → A 确认图

1. **看图报框**：逐件给出 `名称 + 框`。框由**看图**得出，不是 OCR 出来的文字框（§2.1.1）。
   认得准不准按 §2.1「关键判断连依据一起写」的三档写进物项表：认准了直接写；
   有依据的推断写结论 + 一句依据（"陶瓷茶壶（壶嘴和把手形状判的，没看到底款）"）；
   **认不出就直接说认不出**并说明缺什么——🔴 编一个像模像样的品牌型号，比留空糟得多；
2. **先探一下这台机器画不画得了图**：`python3 scripts/annotate.py probe`；
3. **出 A 确认图**（物项表按 stdin 递给脚本，序号从 1 连续编；
   多图分批时第二张图接着上一张往下编，写法见本节末「单图 / 多图」）：

   ```bash
   python3 scripts/annotate.py render --image /path/pile.jpg --form A --numbering fresh <<'JSON'
   {"items":[{"no":1,"name":"手机支架","box":[255,195,1195,555]},
             {"no":2,"name":"陶瓷茶壶","box":[520,705,915,1075]}]}
   JSON
   ```

   结果是一行 JSON：`outputs[].path` 是图、`dir` 是这一轮的临时目录、`warnings` 要念给主人听。
   **用 Read 工具把图看一眼再给主人**（§1「Claude Code 宿主取图法」同一条路数）。

🔴 **确认图、预览图永远不 `photo upload`**。§4 那条"敏感检查在上传之前"保护的是
"传上去就有公开可读的 URL"；确认图只走本地路径给主人看，所以它排在敏感检查之前不违规。

**画不了图的时候（没装 Pillow）——能力少了，流程不断**：脚本会回
`{"ok": false, "error": "pil_missing"}` 并带上引导语，此时
① 仍然逐件识别、仍然出物项表，只是**文字版**（序号 + 名称 + 大致位置："左上""中间偏下"）；
② 门 1 用文字表代替确认图，确认门**照样过**；③ 封面用原图（与今天一模一样，不比现状差）；
④ 一句话告诉主人："你这台机器上没装图片处理库（Pillow），所以我只能给你文字清单、
画不了标注图。装的话一句 `pip install Pillow`，装完跟我说一声。"
🔴 **不替主人装依赖**——装东西到他机器上是他的决定，引导即可。
脚本回 `font.ascii_only: true` 时同理：图上只有框和序号，名称在对话里说，别硬塞进图。

#### 2.4.2 🚪 门 1（必过，不可跳）

一屏内给主人看四样东西：

1. **物项表**——序号 / 名称 / 成色 / 挂价（带来源：图上标价 or 建议价，承 §2.1.2）；
2. **A 确认图**；
3. **图质建议**——见下，每件一句，**没建议就不写**；
4. **组合建议**——见下，**默认为空**，有话说时必须是问句。

**同屏合并追问**：§2.3 A 档"认不出的品名"在这里问（**不占 §3 额度**，§2.3 原文），
B 档的两问也挂在这一屏。主人正对着图、指着框回答，成本最低——
原来只能在建档之后用文字问"那个粉色瓶子是什么"，主人还得回想是哪个；
现在"④ 是我的护手霜"一句话就答完。**问了主人也不知道** → 走 §2.2 分件清单的既有出口：
并进「等 N 件」收尾，或那一行如实标未知，**不发明新出口**。

🔴 **硬条款：门 1 未过 → 不得 `photo upload`、不得 `listing create`。**

🔴 **门 1 是一个高产的口述现场，§5.0 的回读范围必须覆盖它。** 主人对着图说的
"3 号不是茶壶是杯子""1 和 5 是一套""那个杯子边上有个小磕""2 号别卖了"
**全是商品事实，不只是改图指令**——处理完就丢，帖子就残缺了。

**主人怎么改一个框——用序号说话，不报坐标**（他要是得报像素，这道门就是摆设）：

| 主人说 | 你做 |
|---|---|
| "3 号不是茶壶，是个杯子" | 只改名字，框不动，**不重出图**（改个名不值得让主人再看一张） |
| "你漏了左下角那个包" | 补一个框，**重出确认图** |
| "4 号那个框把相机带子切掉了" | 按描述扩框，**重出确认图** |
| "2 号别卖了" | 从物项表删掉，重出确认图（或口头确认，不重出） |
| "1 和 5 是一套" | 归到同一帖，重出图时**用同色框** |

三条纪律：**图上永远有序号**（标签写「① 品名」，序号是主人和你之间唯一的共同坐标系）；
**改名不重出图、改框才重出**；🔴 **改框最多两轮**。

**退出条件——框错 ≥3 件、或改到第二轮还不对 → 主动收手**，给两条路让主人选：

> "这张图我拆不太准。要么就用原图发一条合集帖——描述里我把每件一行列清楚，带编号、
> 各写各的价和成色，买家能直接点着号问；要么你把想单独发的那件重拍一张给我——你说哪种？"

这条退路不是"退回一个将就的现状"：§2.2 的分件清单本来就是完整能力，
**图像侧失败 ≠ 整条链失败**。所以**该早收手就早收手**，别把确认拖成拉锯——
拉锯的成本全落在主人身上，而那正是这个能力要消灭的东西。

**图质建议：给框架，不给阈值表。** 三个出口：`直接发` / `建议补拍` / `建议单拍`。
逐件问自己（答不上来本身就是信号）：能不能认出**是什么**？能不能判断**成色**、瑕疵看得见吗？
这件被**压住/遮住**了吗、框和框重叠得厉害吗？画面里有没有**与本帖无关的东西成了视觉主体**？
光线清晰度**是否影响上面三条**（判的不是"清不清晰"，是"清晰度不够到影响买家判断了吗"）。

| 情形 | 默认给什么（可被你的具体判断覆盖） |
|---|---|
| 三条都过 | **直接发**——一个字不多说 |
| 认得出、成色判不了 | **建议补 1–2 张关键角度**（正面 + 瑕疵处），**不是"重拍整张"**（承 §1 口径） |
| 认不出是什么 | **建议单拍这一件** |
| 框严重重叠 / 被遮 | 建议单拍被遮的那件；整张图仍可当合集封面 |

"值得单独拍一张"的判据 🔴 **明确禁止用金额阈值**，判的是**信息密度需求**：买家需要看清
具体的字才敢买（铭牌、型号、序列号、成分表、尺码标）· 成色直接决定价格区间（数码/相机/
乐器/名牌包）· 买家一定会追问细节（能不能开机、配件全不全、镜头有没有霉）· 它在这堆里
明显比别的贵一个量级（**只作辅助信号，不单独成立**）。命中 ≥2 条 → 建议单拍；命中 1 条自己权衡。

🔴 两条兜底：**拿不准就问主人**（占 §3 额度）；**任何"建议补拍/单拍"都不得阻塞发布**——
话术是"发出去之后随时补"，不是"补了再发"。以**重拍**为前置比以拍照为前置挡得更狠，
那会把 §0 撞碎。
🔴 **D 档禁问是硬的，图质建议不得当绕道**：不许借"图上看不出有没有原包装 / 配件全不全"
把 §2.3 D 档那张禁问清单从侧门拆了。图质建议只回答一件事：
**这张图作为素材，够不够买家判断**，不问物品身世。

**组合建议纪律（逐条照做，这是禁止式条款）**：

```
禁 1  不得把任何价格门槛读成捆绑授权。
      「起码 20 磅一单」「低于 X 不出」「太便宜的懒得寄」是**成交门槛**——
      它只影响"要不要接受某个报价"，不影响"哪几件放进同一个帖子"。
禁 2  不得为了凑到某个金额，而把物品放进同一帖。
禁 3  不得因为"两件出现在同一张照片里"就合成一帖。同框是拍摄事实，不是售卖意图。
禁 4  未经主人明说，不得跨品类打包。可以**建议**的组合仅限**真语义关联**：
      同一套 / 同一系统 / 同场景成套使用（厨房四件套算 · 同一台相机的电池和充电器算
      · 同系列的书算）。❌「都是小件」不算 ·「都不好卖」不算 ·「加起来刚好 20 磅」不算。
禁 5  建议 ≠ 执行。任何组合或拆分必须以**问句**出现在门 1 的回显里，默认值是**不组合**。
      主人不回应 = 不组合，不得沉默执行。
禁 6  §2.2「毕业清屋」的"打包价主动问一句"仍然有效，但它问的是**整批**打包价
      （全都一起拿走多少），**不是授权你自己挑子集去凑包**。子集打包只在主人明说时做。
自检  回显里每出现一句"建议把 X 和 Y 放一起"，必须能指出**主人的哪句原话**或
      **哪条真语义关联**支持它。指不出来 → 不许出现。
```

**拆帖还是合集帖——判据不是件数，是「买家会分开搜吗」**：

| 情形 | 走法 |
|---|---|
| 每件都能被单独搜到、单独定价、单独成交（相机 / 茶壶 / 微波炉） | **拆帖**，每帖一个 B 封面 |
| 一堆同类小件，单件价值低，买家不会只要其中一个（护肤小样 / 一箱书 / 一袋文具） | **合集帖**，文字侧整段照用 §2.2 分件清单；封面用 B 或原图 |
| 主人明说了 | 按主人的 |

**默认倾向：能拆就拆**（拆帖是给每件独立封面的唯一路径，帖子只有一个封面字段）。
但要给这条倾向降温：合集帖里每件已经有自己的编号、价格、成色、逐件例外，买家搜得到、
点得着号问，**拆帖换来的只剩独立封面 + 独立的帖级字段**。所以**不要因为"拆开好看"而拆**；
主人嫌麻烦就合，合了也不残废。拆帖的成本要诚实说：拆 5 帖 = 5 次上架 + 5 条帖要擦亮 +
可能 5 条串要回，**建议上限 ≤ 8 帖/次**。触发拆帖的信号直接复用 §2.2 那两条
（超 ~10 件、清单超 ~8 行），**不另立第三套数**；两个闸打架取较严的那个，
并把理由讲给主人听（"12 件我建议分两批，一次发 8 条你回消息才顾得过来"）。

**混合情形**（一张图里既有该单发的、也有该打包的）：允许一次同时产出
「N 条单品帖 + 1 条合集帖」。这时 **发布前主人只用一套号**（物项表的号）；
合集帖的清单**从 1 开始连续编自己的号**（不跳号，跳号在买家眼里就是 bug）；
🔴 **托管清单里必须有一列写清对照**——「物项 5 → 合集帖 2 号」，主人说"5 号"你要能一步对上。

#### 2.4.3 🚪 门 2（点头即执行，不再问）

主人点头**之后**才正式加工，按最终物项表出每帖封面。产物随托管清单一起回显，
主人仍可说"这张封面重出一版"。**门 2 不再单独设一次确认**——再加一道会把
"30 秒过目"变成"三轮来回"，直接伤"省心"。

| 形态 | 命令 | 用在哪 | 默认 |
|---|---|---|---|
| **A 确认图** | `--form A` | 门 1 回显 | **标配**，每次一图多物都出 |
| **B 聚焦封面**（其余压暗、本帖商品原亮度，零裁剪零信息丢失） | `--form B --only 1,3` | 每帖封面 | **多件同图时的默认封面** |
| **C 裁剪图**（按框裁出单件，干净无标注） | `--form C --only 4` | 备选封面 / 主人要"下载了发群" | 主人开口才给 |
| **D 价签总览**（每件贴「序号 + 名称 + 挂价」，已出的打叉保留原号） | `--form D` | 门 2 之后的外发物料 | **不默认出，主人开口才出** |

**B 为什么是默认封面而不是 C**：B 零裁剪、买家点进去仍看得到整个环境；C 裁得干净，
但把"这是一个人在清屋"的语境裁掉了，而那个语境正是留学生二手圈的信任来源
（同一栋楼、同一间宿舍）。C 的最佳位置是"主人自己下载了发群"，那时不需要平台语境。

**D 附三条硬条款**：
- 出 D 图时必须一句话告知：「**这张是此刻的快照，价格或状态变了要跟我说一声重出一张**」；
- **D 图不自动同步为帖子封面**——不让一张会过期的图成为长期门面；
- 🔴 **重出 D 图前先读回帖子描述**，按清单行的号和 `❌已出` 画。"谁已经出了"完全由
  清单行给定（那是 marketplace.md §A 规定主人卖掉一件时必改的东西）：
  我们既不猜、也不探测成交，**更不为它建一份状态**。

**加工产物照常走既有链路，不绕过**：仍经 §4 敏感信息检查 → `photo upload`
（元数据剥离 + 签名直传）。🔴 **加工产物要再过一次敏感检查**——裁剪可能把原本
判"要裁掉"的区域留下来，标注图会把**整张原图**带出去。加工**只读原图，绝不改写原图文件**。

**临时文件**：产物落在系统临时目录下每轮独立的目录（脚本回的 `dir`）。
🔴 不进 `~/.a2hmarket/`（那是状态目录，放进去等于新建一处持久化），🔴 不进工作目录（会被 git 收走）。
**上传成功 → 立刻 `python3 scripts/annotate.py cleanup --dir <dir>`；主人说不要了 → 立刻删。**
会话结束不保证清理，交给系统回收临时目录，**不做定时清理任务**。

🔴 **落盘物零红线**：物项表和图上只能出现 **名称 / 框 / 颜色 / 挂价（公开价）**。
红线 #4 那几样（主人的私有议价策略）不进物项表、不进文件名、不进图上文字、不进图片元数据。

#### 单图 / 多图

**单图多件**是主路。多图时先判**这几张是不是同一堆**：

- **同一堆的不同角度** → 选**一张主图**做框与确认图，其余作补充照片挂到对应帖上，**不重复框**；
- **不同批 / 不同房间** → 逐图独立走一遍，一图一张确认图；托管清单**合并成一张表**
  （不要出 N 张表轰炸主人）；
- **判不出来** → 问一句"这几张是同一堆的不同角度，还是不同的东西？"（占 §3 额度）。

**一次处理上限 ≤ 6 张**（超了先处理前 6 张、告知还剩几张、问要不要继续）。
理由：一屏塞十几张确认图，主人根本过不了目，门 1 就形同虚设。这是产品边界，可调。

🔴 **合并成一张表 = 一套连续的号，第二张图的件接着上一张往下编。**
合并表里既然只有一套号，图上的号就得跟着它走：第一张图出到 3 号，第二张图那两件
在表里是 4、5，**图上也画 4、5**——出图时把这句话显式说给脚本听：

```bash
# 第一张图：三件，1..3（不给 --first-number 就是从 1 起）
python3 scripts/annotate.py render --image /path/kitchen.jpg --form A --numbering fresh <<'JSON'
{"items":[{"no":1,...},{"no":2,...},{"no":3,...}]}
JSON
# 第二张图：两件，在合并表里接着编 4、5
python3 scripts/annotate.py render --image /path/desk.jpg --form A --numbering fresh --first-number 4 <<'JSON'
{"items":[{"no":4,...},{"no":5,...}]}
JSON
```

三条纪律：

- **起点由你当轮说出来，脚本不记也不猜**——它没有"上次编到几号"这种记忆，
  也不许有（那是持久化后门）。合并表在你手上，起点从表上数；
- 🔴 **`--first-number` 是声明不是放松**：声明 4 就要求这批的号正好是 4、5、6…，
  跳号、重号照拒。**不许调这个数去迁就手里已经乱掉的号**——那样合并表上就有洞了，
  而买家是点着号来问的；
- **这一切只发生在发布前**。一旦 `listing create` 落地，号就固化在帖子描述的分件清单里，
  此后一律 `--numbering listing` 按清单行的号画，`--first-number` 在那条路上会被脚本拒掉
  （已发布的号只有清单这一个真相源，不接受外面另立起点）。

## 3. 追问规则（一次最多 2 问，一问不问也可以）

每多一次追问都在压低"愿不愿意发"。能推断的不问、留空不影响发布的不问、
用户已经说过的**绝不重复问**。

额度优先花在 §2.3 的 **B 档**（地点到楼、能否正常用）；A 档的两问不占额度；
C/D 档**任何情况都不为它们花额度**。要不要用掉追问额度，
参考**买家真正关心什么**来判断：

- 能不能正常使用（数码家电类）
- 关键配件在不在（充电器/包装，影响定价档）
- 照片上看不出的隐性毛病
- 尺寸/重量、好不好搬（家具大件类）
- 多久之内要出手（影响定价节奏与挂帖时长）

**这是判断素材，不是必问清单**——结合具体物品挑出最多两个真正值得问的；
信息够了就一个不问，直接出清单（缺的字段在清单里留空，用户过目时自己会补）。
批量托管时合并追问（"这几件里有不能正常用的吗？"），不逐件轰炸。

## 4. 敏感信息检查（🔴 **在 `photo upload` 之前**，不是上架前）

**顺序是硬的：看图 → 敏感信息检查 → 上传 → 建档 → 上架。**
不合格的图**根本不要传**——传上去就有了公开可读的 URL，之后再从帖子里摘掉引用
**只是不再展示，对象仍在**，要真正删除得有存储权限，多数时候当场做不到。

> 实测事故（2026-08-05 批量导入）：一张"收纳架"照片里，架子上的箱子贴着快递面单，
> 可读出收件人姓氏与伦敦门牌号。**图先传了、帖先发了，逐张看图时才发现**——
> 补救只能摘引用，对象删不掉。当时的流程是「先传后看」，规则写的是"上架前"，
> 于是"上架前"被理解成了"发帖那一刻之前"，而上传早就发生了。**所以这里改成
> 以 `photo upload` 为界**。

你要检查的是**照片里看得见的东西**，逐张过：

- 快递单/收货地址/手机号 → 提醒用户重拍或裁剪；**注意它常在背景里**
  （箱子、桌上的信封、屏幕），不只出现在"主体"上；
- 证件、屏幕上的个人信息 → 同上；
- 人脸、明显的家庭环境细节 → 提示用户确认是否介意。

> 📍 **位置口径**：留学生场景的信任恰恰来自"同一栋楼、同一个学校"——
> 位置**精确到公寓楼/宿舍/最近地铁站**（"Astor College"），不再刻意模糊。
> 发帖 `--location` 默认带档案的常驻地点（`profile get` 的 `residenceLocation`），单条可覆盖。

有问题的照片**不上架**，在清单中标注"待换图"。

🔴 **加工产物同样要过这一节**（§2.4 出的标注图 / 聚焦封面 / 裁剪图）：裁剪可能把原本
判"要裁掉"的区域留下来，标注图则会把**整张原图**带出去——原图没过的，加工完照样不能传。

> ✅ **看不见的那部分（EXIF）不用你管**：`a2hmarket.py photo upload` 会在上传前剥掉
> GPS、拍摄时间、机身型号、内嵌缩略图和注释，只保留方向标记（不保留的话竖拍照片
> 会在集市上转 90°）。图像数据本身逐字节不动，不重新编码、不损画质。
>
> 🔴 **这一条别当成"敏感信息检查可以省了"**：EXIF 里的 GPS 是自动剥的，
> 但照片里拍到的快递单、证件、人脸，机器看不出来——那仍然是上面这四条的职责。

## 5. 输出托管清单

**一次抽完再回显，不要连环追问**：把已知的信息一次性全部填进表，
缺的字段留空或标「未知」——清单本身就是最后一道确认，缺什么用户扫一眼看得见，
想补随口一句就行。发布门槛低（一句话就能发），但最后的信息都经用户过目。

### 5.0 🔴 出清单前：口述落位核对（工序，不是态度）

清单落笔之前，**回读本次会话里用户说过的每一句商品相关的话**（包括顺口带的），
逐条核对：它已经落进结构化字段、描述、或清单备注**三者之一**了吗？漏了就补上，
拿不准落哪的进描述。**核对没做完不出清单**——和 §2.1"看图是工序"同级。
唯一例外：**卡里标了敏感例外的项不落位**（如 card-carpool 的航班号——禁问也禁记，
主人顺口报了也不落帖不入档，回显时说明为什么没写）——卡的敏感条款压过本工序。

| 用户顺口说的 | 落点 |
|---|---|
| "买了三年了" | `--attr 购入时间=…` 或描述 |
| "充电器找不到了" | 瑕疵/描述（配件不齐是买家必知项） |
| "可小刀" "只收现金" | 描述【交易】行（§2.0 的分流表） |
| "周末才能自提" | 描述【交易】行 |
| "别挂太贵，能出就行" | 定价依据 + 清单备注（影响议价授权） |
| "这个和那个锅是一套的" | 描述（关联信息丢了买家就拆着买） |

为什么是硬工序：典型事故是用户口述了三条细节、清单里一条都没有——
**用户确认的是残缺清单，发出去的就是残缺帖**，之后每一条缺失都变成
微信里的一次重复提问。§1 那句"顺口说的信息全部记入建档"是态度，这里是闸。

一张表让用户 30 秒过完，格式：

```
📦 托管清单（N 件）——过一眼，没问题我就开摊

| # | 物品 | 成色 | 挂价 | 备注 |
|---|------|------|---------|------|
| 1 | Kindle Paperwhite 4 8G | 轻微使用痕迹 | £15（图上标价） | 屏幕左下角浅划痕已注明 |
| 2 | 电饭煲 | 明显使用痕迹 | £8（建议价） | 图上无价，按行情估的 |

可以直接说"3 号别卖了""2 号 50 就行"，我来改。
```

- 挂价列**带币种、注来源**：图上有标价的写图价并注「图上标价」（见 §2.1.2）；
  图上无价的才用 [pricing.md](pricing.md) 的建议价，注「建议价」——
  让用户一眼分得清哪个是自己定的、哪个是 AI 估的；
- 用户的任何单条修改直接执行，不反问；
- 用户确认后 → 进入 [authorization.md](authorization.md) 对齐总授权（首次托管）或直接上架（授权已有）。

## 6. 建档产出去向

- 公开字段（契约 listing 部分）→ 待上架，见 [marketplace.md](marketplace.md)；
- 私有字段（底价/档位）→ **只在当轮会话里存在，不落盘**（红线 #4，条款见 [pricing.md](pricing.md) §5）。
